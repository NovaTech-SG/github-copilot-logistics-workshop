**Feature Branch**: `main`（本阶段未创建或切换分支；功能目录独立编号）

**Created**: 2026-11-16

**Status**: Draft

**Input**: User description: "参考 mockup/index.html 和 docs/data-source.md，为现有异常队列新增跟进状态与备注的本机 SQLite 保存功能，保存后重新读取确认，刷新或同库重启后仍保留结果，Databricks 源数据保持只读。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 保存单条异常并确认结果 (Priority: P1)

物流跟进人员在已有异常详情中选择处理状态、填写备注并保存。系统重新读取同一异常，确认状态与备注均与本次提交一致后，才告知保存成功，避免把仅发出请求当作已完成。

**Why this priority**: 跟进动作需要可靠落地，用户必须能够区分已确认完成和仍需核对的结果。

**Independent Test**: 选择一条待处理异常，填写备注并推进为处理中，核对重新读取的异常编号、状态与备注以及最终提示。

**Acceptance Scenarios**:

1. **Given** 一条当前为 OPEN 的异常，**When** 用户选择 IN_PROGRESS 并填写有效备注保存，**Then** 本机记录保存成功，重新读取同一异常且状态与规范化后的备注一致后，页面显示“已保存到本机，并重新读取确认”。
2. **Given** 一条当前为 IN_PROGRESS 的异常，**When** 用户选择 RESOLVED 并填写有效备注保存，**Then** 确认结果显示已解决及本次备注。
3. **Given** 当前状态为任一合法状态，**When** 用户保持状态不变并更新有效备注，**Then** 本机记录更新，重读确认后展示该备注。
4. **Given** 保存或后续核对正在进行，**When** 用户再次点击保存，**Then** 页面显示处理中且不能产生第二次提交，流程结束后恢复可操作状态。
5. **Given** 写入已返回成功，**When** 后续读取失败或编号、状态、备注任一不一致，**Then** 页面明确提示“已提交但尚未确认”，不显示成功，并允许重新读取核对。
6. **Given** 保存被明确拒绝或发生本机写入失败，**When** 用户查看反馈，**Then** 页面显示保存失败及可理解原因，已保存记录不变；若连接中断导致提交结果无法确定，明确提示结果未确认并引导重新读取，不宣称已成功或确定未写入。

### User Story 2 - 刷新和同库重启后继续跟进 (Priority: P2)

跟进人员重新打开页面或重新启动本机服务后，仍能看到此前保存的状态、备注和本机保存时间，并能区分源记录与本机跟进结果。

**Why this priority**: 记录必须跨页面和服务生命周期保留，才能支持后续持续跟进。

**Independent Test**: 使用预先保存的一条本机记录，分别刷新页面及使用同一存储文件重启服务，核对详情、队列和概览。

**Acceptance Scenarios**:

1. **Given** 某异常已有确认的本机记录，**When** 刷新或重新打开页面，**Then** 该异常仍展示保存的状态、备注和本机保存时间。
2. **Given** 已记录当前使用的存储文件且源记录仍可读取，**When** 停止服务并用同一文件重启，**Then** 原跟进结果完整恢复。
3. **Given** 源状态为 OPEN、本机保存为 IN_PROGRESS，**When** 重新读取队列及详情，**Then** 队列、状态筛选及概览采用本机合并后的状态，详情仍能区分源状态、源更新时间与本机状态、本机保存时间。
4. **Given** 某异常没有本机记录，**When** 读取详情或队列，**Then** 继续展示源结果；更换存储文件后按新文件中的记录展示，不将不同文件视为同一份记录。

### User Story 3 - 拒绝无效或过期跟进且保持异常独立 (Priority: P1)

跟进人员获得明确的规则反馈，旧页面不能覆盖已经推进的状态，同一运输单上的其他异常和只读源记录保持独立。

**Why this priority**: 防止错误状态、无效备注和过期操作破坏跟进记录是保存功能的必要保障。

**Independent Test**: 对预置异常分别提交无效状态、边界备注和过期原状态，并比较保存前后目标异常、同单其他异常及源记录。

**Acceptance Scenarios**:

1. **Given** 当前状态为 OPEN，**When** 直接改为 RESOLVED，**Then** 拒绝保存并说明只能逐级推进，已有记录不变。
2. **Given** 当前状态为 IN_PROGRESS 或 RESOLVED，**When** 尝试退回此前状态，**Then** 拒绝保存且不产生部分更新。
3. **Given** 备注为空、仅空白或去首尾空格后超过 1000 字，**When** 保存，**Then** 拒绝并说明备注规则；去首尾空格后恰好 1000 字的有效备注可以保存。
4. **Given** 页面读取的原状态为 OPEN，而当前有效状态已由另一操作推进为 IN_PROGRESS，**When** 页面仍以原状态 OPEN 提交，**Then** 拒绝覆盖并提示重新读取，即使目标状态本身合法也不得覆盖。
5. **Given** 两条异常属于同一运输单，**When** 保存其中一条，**Then** 仅该异常的本机记录变化，另一条异常及全部源字段不变。
6. **Given** 异常不存在、状态值无效或缺少原状态，**When** 提交保存，**Then** 明确拒绝且不创建或改变本机跟进记录。

### Edge Cases

- 保存前尚无本机记录时，以当前源状态作为有效状态；已有本机记录时，以合并后的状态校验原状态及推进规则。
- 备注保存前去掉首尾空格，以处理后的内容做必填、长度校验与重读比较。
- 状态推进至 RESOLVED 后仍允许保持该状态更新备注，不允许退回。
- 写入失败时，状态、备注与本机保存时间均保持原值，不留下半条更新。
- 写入成功后源读取失败，记录可能已持久保存，提示未确认并提供重新读取入口，避免误导用户反复保存。
- 保存流程中切换异常或较早请求延迟返回时，反馈必须对应本次提交的异常，不把另一条异常的结果当作确认。
- 源查询失败时明确报错，不用效果稿固定样例或本地模拟业务数据代替真实结果。
- 原状态相同的并发备注更新沿用现有原状态校验边界，本轮不新增完整版本控制或备注历史。

## Requirements *(mandatory)*


### Functional Requirements

- **FR-001**: 系统必须按异常唯一编号（exception_id）保存处理状态与备注，同一运输单的不同异常独立。
- **FR-002**: 系统必须仅允许 OPEN → IN_PROGRESS → RESOLVED 逐级推进，允许同状态更新备注，拒绝跳级、退回或未知状态。
- **FR-003**: 备注必须去首尾空格后必填且最多 1000 字，保存及确认均采用处理后的内容。
- **FR-004**: 提交必须携带页面读取时的原状态，与保存时当前有效状态比较；缺失或不一致时拒绝覆盖并提示重新读取。
- **FR-005**: 状态、备注与本机保存时间必须完整保存；校验失败、异常不存在或写入失败不得产生部分更新或无效记录。
- **FR-006**: 保存得到成功响应后，页面必须重新读取同一异常，核对编号、状态与备注全部一致后才显示成功。
- **FR-007**: 页面必须区分明确的保存失败、已提交但尚未确认及重读确认成功；重读失败或不匹配不显示成功，允许重新读取核对。提交连接中断而结果不确定时必须提示未确认，不宣称确定未写入。
- **FR-008**: 从提交开始至核对结束必须显示处理中并防止重复提交，结束后恢复操作；延迟返回不得确认到其他异常。
- **FR-009**: 保存结果必须在刷新、重新打开页面及使用同一存储文件重启后保留；重新读取的队列、筛选、概览和详情按已有合并规则反映结果。
- **FR-010**: 页面必须区分源状态、源更新时间与本机状态、本机保存时间；没有本机记录时沿用源结果。
- **FR-011**: Databricks 源数据必须保持只读，不改变同单其他异常；查询失败必须报错，不用效果稿固定数据或模拟结果兜底。
- **FR-012**: 本轮必须保留已有列表、详情、搜索筛选、分页、查询与页面布局，复用现有校验和本机合并能力，仅新增保存与确认反馈。
- **FR-013**: 凭据必须仅在后端使用，不得输出或进入页面和生成产物；本机记录文件不得作为共享代码产物提交。

### Key Entities *(include if feature involves data)*

- **源异常**: 以异常编号唯一标识，关联运输单与承运商背景，包含源状态、备注和源更新时间，对本功能保持只读。
- **本机跟进记录**: 关联单个异常编号，包含本机状态、规范化备注和本机保存时间；仅保留当前结果。
- **跟进提交**: 某异常的原状态、目标状态和备注，用于规则及过期状态校验。
- **确认结果**: 提交后重新读取的有效结果，编号、状态和备注全部匹配才可确认成功。

## Success Criteria *(mandatory)*


### Measurable Outcomes

- **SC-001**: 两种逐级推进与三个合法状态下同状态备注更新共五类操作全部通过，每次成功提示均有同一异常重读且内容一致的证据。
- **SC-002**: 刷新、重新打开页面及使用同一存储文件重启三类恢复检查中，保存状态与备注的一致率为 100%。
- **SC-003**: 空白备注、超长、跳级、退回、未知状态、缺少原状态、过期原状态及不存在异常八类拒绝场景均不改变已有记录；1 字与 1000 字有效备注均可保存。
- **SC-004**: 明确写入失败、提交结果不确定、重读失败和重读不匹配四类故障验收中，错误成功提示次数为 0，用户均可识别失败或未确认并能重新读取。
- **SC-005**: 保存同单一条异常后，另一条异常和源记录的非预期变化为 0；重读队列、筛选、概览及详情全部与有效状态一致。
- **SC-006**: 保存及确认期间连续点击保存至少三次仅产生一次提交，流程结束后可继续操作。

## Assumptions

- 本功能面向已有异常队列的本机使用者，沿用当前访问方式，不增加账号、权限、跨设备同步或多人协作系统。
- 用户指定本项目 SQLite 为本机存储、Databricks 为只读源；这是既定约束，具体写入与交互实现留到计划阶段。
- 已有校验、存储结构、连接和本机合并能力继续复用，不重写读取链路。
- 重读与恢复验收依赖源查询可用且异常仍存在；源不可用时明确报错，不承诺离线查看业务队列。
- 同库重启指沿用同一存储文件；更换文件代表另一份记录，不提供迁移、自动清理或跨文件合并。
- 过期检测沿用原状态比较，不扩展为同状态并发备注的版本冲突检测；后一次合法保存更新当前备注。
- 效果稿只用于理解目标布局及交互，其中固定编号、数量和时间不作为实际数据或验收结果。
- 验收分别记录离线检查、实时源查询、页面保存确认及同库重启恢复。本阶段只生成规格与质量检查，不代表保存功能已经实现或验证。
